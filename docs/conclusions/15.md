# N56 · iOS 15.8.8

15.8.8（19H422）是 iPhone 6 Plus 的第三个系统，装在独立的 System15 / Data15 卷上，和 iOS 12.5.8（16H88，原机）共用一个 APFS 容器。内核、系统镜像和 rootfs 底包来自 J96（iPad mini 4），同版本驱动和 iPhone 资源来自 N66（6s Plus），原生硬件材料（SEP 固件、Mav10 基带、B1 Wi-Fi 固件、校准与机型文件）仍来自 N56 原机。

截至 2026-11-19，从刷机后的干净设备执行一次 `all` 可以装完：开机进系统、全部硬件可用、加密 Data15、激活、palera1n rootless 越狱、Sileo 和 SSH。

## 刷机后一次跑通

### 前提

- 设备刷回 iOS 12.5.8（16H88）。刷机后 APTicket 会变，旧的 `state/IM4M.bin` 和旧启动包都会失效，`all` 会自动重新提取。
- `ipsw/` 下放三个 IPSW，文件名不变：

  ```text
  ipsw/iPhone_5.5_12.5.8_16H88_Restore.ipsw            # N56
  ipsw/iPhone_5.5_15.8.8_19H422_Restore.ipsw           # N66
  ipsw/iPad_64bit_TouchID_15.8.8_19H422_Restore.ipsw   # J96
  ```

- rootless/rootful 用到的上游包（binpack、procursus bootstrap、Sileo 等）都固定了 SHA256。先执行 `python3 -m patches.ios15.impl.rootfs.rootless_bootstrap`，一次性下载到 `ipsw/cache/ios15-rootless/`，之后构建不再联网。
- 环境按 README 准备，Intel 和 Apple Silicon 宿主都可以。`tools/doctor.py --target n56-ios15` 可检查宿主环境。

### 命令

设备进 DFU，然后：

```sh
sudo python3 n56patcher.py all --target n56-ios15
# 或者网页界面：sudo python3 gui.py，目标选 n56-ios15，阶段选“端到端”
```

Data15 默认加密（`--data-protection none` 可改为不加密），越狱默认 rootless（`--jailbreak-mode rootful` 可切换）。

流程：init（派生输入、解密 iBSS/iBEC）→ 进 ramdisk → 重提 IM4M → 建 System15/Data15 卷 → 构建五件套 → 写入 J96 系统镜像 → 打全部 rootfs 补丁 → 启动。和 13/14 不同，15 先构建再写系统卷：System15 不 seal，写入前 `system_policy.before_system_write` 要确认五件 IMG4 与当前 IM4M 一致、功能选择与 build 一致、KPF → SSV 证明链完整、卷上没有 seal 或 snapshot。已有 seal 或 snapshot 时直接拒绝，不会自动删除。

通过宗卷安装（GUI 或 `n56patcher.py slots install 15`）时，工作目录固定为 `build/slots/15`，装完记入 `state/volumes.json`。之后再开机：设备进 DFU，GUI 里启动 15，或执行 `python3 n56patcher.py boot --slot 15`。

### 首次开机

- 根是只读的 System15。stage0 先把 Data15 的 `/private/var` 重挂为 `suid,nodev`，runtime 随后用 statfs 复查确实没有 `nosuid`，再进入 Data15 上的 bootstrap。`/var/jb` 指向这份 bootstrap。
- SSH 走 Wi-Fi 或 USB 都可以；sudo 和 Sileo 的 `giveMeRoot` 都依赖上面的 suid 挂载。
- 出现失败时，先保留串口日志和 panic 信息，不要反复刷写或重建 systembag。

## 空间

- J96 19H422 的 dyld cache 被拆成主文件、`.1` 到 `.5` 和 `.symbols`，共 2,324 个镜像。`core/dyld_cache.py` 是只读读取层，按 VM 地址定位到子文件。
- 系统卷沿用 14 的 decmpfs 透明压缩写入。
- 16 GB 机型空间很紧，安装前按 14 的方法先用 `fsck_apfs` 估算剩余空间（见 [14.md](14.md) 的“空间”一节）。

## 关键适配（相对 14）

- **越狱与 SSV**：palera1n KPF 不注册 `apfs_patch_rename`；SSV guard 在 KPF 之后最后应用，System15 以 livefs 方式启动。
- **音频**：入口和 14 相同（N56 原生 CS42L67），但 15 的 ABI 差异更大：先在当前 KC 的空余 padding 里暂存原生代码，再闭合布局、继承关系和私有入口，最后把七个剩余入口接到 15 的原生函数上，并发布 personality。prelink 给 CS42L81 补 `OSBundleCompatibleVersion`（否则依赖解析失败、类不注册）；补两处被分支隔开的虚调用（0xa60→0xaa8、0xa80→0xac8）；stop/timer 回调 stub 的私有字段按相对原生 +16 补（0x1c8→0x1d8、0x1c0→0x1d0），只补 +8 会把标志位写进对象指针导致 panic。VirtualAudio 保持原版。12 → 14 → 15 的对照事实固定在 `audio-abi-profile.json` / `audio-final-profile.json`。
- **SEP**：沿用旧协议桥（固定端点、SKS v0、SCRD、SSE）。现代 media/file 包装统一转换到 v0，SKS61 只接受空 cookie。SKS15 重封装与 SKS16 新密钥生成的请求 flags 对齐 13/14：`0x1c → 0xc`；重封装的空附加输出保持 `0`。新密钥的盘上包装输出接到 v2 第四组，对应 13 的第三组。
- **激活 UIK**：15 的 `mobileactivationd` 让 SEP 维护系统 UIK（`osko`，selector 43 → SKS34），12 的 SEP 不支持，返回 -12。`rootfs.activation_legacy_sep` 把 `copy_uik` 和 UIK 的 bump/commit 接到 `/usr/lib/n56-mobileactivation.dylib`，按 14 的方式生成 SEA 引用密钥（`kSecAttrAccessibleAlwaysThisDeviceOnlyPrivate` + PrivateKeyUsage），引用存进 mobileactivationd 系统容器的 `Library/uik`。`copy_uik` 返回 +1 引用，不能 autorelease。
- **蓝牙**：bluetoothd 沿用 14 的 4 处同槽位改写（借 BCM_4350C2 组）。15 的 WirelessRadioManagerd 开机时向 bluetoothd 推送 LTE 共存参数，bluetoothd 随即下发 HCI MWS Signaling / Channel Parameters，之后 BCM4345 不再上报任何 LE 广播和 inquiry 结果（重启 bluetoothd 时不再推送，所以表现为“重启就好”）。4 个 WCM MWS 处理函数改为直接返回已处理，和 12 的 BCM_4345 分支一样不下发 MWS。
- **相机**：AVGestalt 的 `_devices` 表里没有 N56，所有 AVGQ 相机能力为空（系统相机只有前置、不能录像）。把 N66 条目改名为 N56，并按 A8 裁掉 Live Photo、4K、1080p 慢动作、前置闪光与 HDR。
- **运动、基带、温控**：在 15 的 chained fixups 和新分组上重新定位。各项 VA 编辑合并后统一规划，只调用一次 `plan_edits`。
- **companion**：从 N66 cache 派生 69 个库，派生版本为 7。compact 扫 `__const`/`__data` 的 32 位相对指针时，目标落在新建的 `__EXTRA_OBJC` 的一律跳过：rebuild 把该段紧贴最后一个数据段放置，VWT flags 等整数会被当成指向该段的指针而误平移（0x30007→0x80007，IsNonInline/IsNonPOD 丢失 → existential 内联溢出、堆损坏，表现为健康各处随机崩溃）。
